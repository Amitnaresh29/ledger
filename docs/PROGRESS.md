#### 1. `pom.xml` — the Maven build file

Maven's single config file. POM = Project Object Model. It is the Java equivalent of
`package.json`: it declares which libraries the project needs, and Maven downloads them into
`~/.m2/repository` and puts them on the classpath. **Must sit at the project root, beside `src`.**

| lines | what it does |
|---|---|
| 1-5 | XML declaration and the `<project>` root element with its schema. Pure boilerplate — never edited. |
| 8-13 | **The `<parent>` block.** `spring-boot-starter-parent` version `3.5.16` is a *dependency management* POM: it declares tested versions for ~300 libraries. This is why every dependency below omits `<version>`. Also sets compiler defaults. **Interview answer: this is how Boot solves dependency hell.** |
| 16-19 | Project identity. `groupId` + `artifactId` + `version` uniquely name the artifact. `SNAPSHOT` = in development, may change. |
| 21-23 | `<java.version>21</java.version>` — the parent reads this to configure the compiler. |
| 27-30 | `spring-boot-starter-web` — REST controllers plus embedded Tomcat. Its presence on the classpath is what makes Boot start a web server. |
| 32-35 | `spring-boot-starter-data-jpa` — Hibernate, Spring Data repositories, transaction management. |
| 37-40 | `spring-boot-starter-validation` — enables `@Valid` on request bodies. |
| 42-45 | `spring-boot-starter-actuator` — `/actuator/health` and metrics endpoints. |
| 47-50 | `flyway-core` — the migration engine. |
| 52-55 | `flyway-database-postgresql` — Flyway 10 split each database into its own module. **Omit this and startup fails with "no database found to handle jdbc:postgresql".** |
| 57-61 | `postgresql` JDBC driver, `<scope>runtime</scope>`. Runtime scope because the code never imports the driver — JDBC loads it by name. Compile scope would allow Postgres-specific imports to leak into business logic. |
| 63-67 | `spring-boot-starter-test` (test scope) — JUnit 5, AssertJ, Mockito, MockMvc. |
| 69-73 | `spring-boot-testcontainers` (test) — wires a container into Spring's test context. |
| 74-78 | `testcontainers:junit-jupiter` (test) — JUnit 5 integration. |
| 80-84 | `testcontainers:postgresql` (test) — starts a real Postgres in Docker per test run. This is why Docker had to be installed. |
| 87-94 | `spring-boot-maven-plugin`. Provides `./mvnw spring-boot:run` and repackages the jar into an executable fat jar. |

**Note:** the whole file is indented two extra spaces. Harmless in XML — cosmetic only.

#### 2. `docker-compose.yml` — the Postgres container

| line | what it does |
|---|---|
| 2 | `services:` — the top-level map of containers. No `version:` key: obsolete in Compose v2 and warns if present. |
| 3 | `postgres:` — the service name. Also its DNS hostname on the compose network. |
| 4 | `image: postgres:17` — **pinned major, never `:latest`.** Reproducible builds, and 17 is inside Flyway 11.7.2's tested range. |
| 5 | `container_name: ledger-postgres` — fixed name so `docker exec ledger-postgres ...` works predictably. |
| 7-9 | `POSTGRES_DB/USER/PASSWORD` — the image's entrypoint reads these on **first start only** and creates the database and role. Fine for local dev; real secrets never go in a committed file. |
| 11 | `"5433:5432"` — **host:container.** Host 5433 because a local Postgres 14/17 already owns 5432. Inside the container Postgres still listens on 5432. |
| 13 | `ledger-pgdata:/var/lib/postgresql/data` — a named volume, so data survives `docker compose down`. This path is the **Postgres 17 convention**; 18+ moved to `/var/lib/postgresql/<major>`. |
| 14-18 | `healthcheck` running `pg_isready`. This is what makes `docker compose up -d --wait` block until Postgres genuinely accepts connections, rather than merely having started. |
| 20-21 | Declares the named volume `ledger-pgdata`. |

#### 3. `src/main/resources/application.properties` — Spring configuration

| line | what it does |
|---|---|
| 1 | `spring.application.name=ledger` — appears in logs and metrics. |
| 4 | `spring.datasource.url=jdbc:postgresql://localhost:5433/ledger` — **note 5433.** |
| 5-6 | Datasource credentials, matching the compose environment. |
| 10 | `spring.jpa.hibernate.ddl-auto=validate` — **the most important line here.** Hibernate may only *verify* that entities match the tables; it must never create or alter them. Flyway is the sole owner of schema. Tutorials use `update`; for a ledger that is disqualifying — no version history, no code review of schema changes, and Hibernate silently omits check constraints, partial indexes and exact `NUMERIC` scale. `validate` also catches entity/schema drift at startup instead of at 2am. |
| 11 | `spring.jpa.open-in-view=false` — turns off Spring's default of holding a database session open for the whole HTTP request. That default causes lazy-loading queries to fire from the view layer, hiding N+1 problems. Off is the professional setting. |
| 12 | `hibernate.jdbc.time_zone=UTC` — Hibernate reads/writes timestamps as UTC. A ledger is an ordered record; ambiguous local times corrupt ordering. |

#### 5. `src/main/resources/db/migration/V1__create_accounts.sql` — first migration

**Filename format is strict:** `V` + version + **two underscores** + description + `.sql`. One
underscore and Flyway silently ignores the file.

| line | what it does |
|---|---|
| 1 | `CREATE TABLE accounts(` |
| 2 | `id UUID PRIMARY KEY` — UUID not auto-increment: sequential integers leak business volume and collide when sharding or merging data. **No `DEFAULT gen_random_uuid()` on purpose** — the application generates the id, so it knows the value before inserting, which matters for logging, tracing and idempotent retries. |
| 3 | `account_type TEXT NOT NULL` — the double-entry classification. |
| 4 | `owner_id UUID NOT NULL` — the holder. One user may hold several accounts. |
| 5 | `currency CHAR(3) NOT NULL` — ISO 4217. Quirk: Postgres `CHAR(n)` is blank-padded and ignores trailing spaces in comparison; the regex check on line 18 protects against that. |
| 6 | `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` — `TIMESTAMPTZ`, never `TIMESTAMP`. Stored as UTC; without a timezone, events cannot be correctly ordered across regions. |
| 8-15 | Named `CHECK` limiting `account_type` to ASSET / LIABILITY / EQUITY / REVENUE / EXPENSE. Enforced in the database, not only in Java, because the database is the last line of defence and the only one that survives a manual `INSERT`. |
| 17-18 | Named `CHECK` that currency matches `^[A-Z]{3}$` (`~` is Postgres regex match). |

**Naming the constraints** (`CONSTRAINT accounts_account_type_check`) was the right instinct: the
name appears in the error message, which is what lets Java catch the exception and map it to a
meaningful API error. Anonymous checks get names like `accounts_check1`.

**`TEXT` + `CHECK` vs alternatives** — a real interview question. A Postgres `ENUM` type is painful
to change. A lookup table with a foreign key adds a join to every read for data that changes once a
decade. `TEXT` + `CHECK` gives database-level enforcement and a one-line migration to change it.

**Verified working:** a valid row inserted; `account_type='WALLET'` rejected; `currency='inr'`
rejected; `currency=NULL` rejected. A constraint that has not been tested is not a constraint.

### Decisions made, and why

| decision | reasoning |
|---|---|
| **Spring Boot 3.5.16, not 4.1.1** | Boot 4 renamed the starters (`-webmvc` not `-web`, split `-test` starters, moved `PostgreSQLContainer`). Every tutorial and StackOverflow answer available while learning is 3.x, so a Boot 4 pom would mismatch every example. Initializr no longer offers 3.x, so the parent version is pinned by hand. |
| **Postgres 17, not 18** | Boot 3.5.16 pins Flyway 11.7.2, which supports Postgres up to 17. PG18 logged an untested-version warning and would need Flyway 13.x — two majors past Boot's tested set. For a correctness-critical project, an untested DB/migration pair is the wrong trade. Also matches the host's `psql` 17 client. |
| **Host port 5433** | A local Postgres 14 + 17 already listens on 127.0.0.1:5432. |
| **`ddl-auto=validate`** | Flyway owns schema; Hibernate verifies only. |
| **No `balance` column on `accounts`** | Balance is derived: `SELECT SUM(amount) FROM ledger_entries WHERE account_id = ?`. A stored balance is a second source of truth that can drift from the journal. A cached balance may come later, but only once the journal is authoritative. |
| **No Lombok** | Hidden generated code works against learning. Java 21 records cover DTOs. |
| **Hand-written pom** | Understanding what the parent POM does is worth more than Initializr output. |

### Mistakes hit, and the lessons

1. **`pom.xml` created inside `src/`, twice.** Maven only finds it at the project root. Lesson: run `pwd` before any file command — `mv` is relative to the shell's current directory.
2. **`./mvnw -q compile` "passed" on an empty class.** An empty class is valid Java. `compile` proves nothing about whether the app works; `spring-boot:run` does.
3. **App failed with `no ServletWebServerFactory bean`.** Cause: `@SpringBootApplication` was missing. Boot knew it was a web app (starter-web on the classpath) but nothing told it to *configure* Tomcat. Lesson: jars on the classpath do nothing on their own — autoconfiguration is what turns them into beans.
4. **App failed with `Failed to configure a DataSource: 'url' attribute is not specified`.** This one was the goal — proof that autoconfiguration was alive and demanding a database.
5. **Postgres 18 container exited on startup.** PG18 moved its data directory to `/var/lib/postgresql/<major>`, so the classic `/var/lib/postgresql/data` mount made it refuse to start rather than risk the data. Resolved by moving to PG17.
6. **No autocomplete in the editor.** Java has no bundled language server (unlike TypeScript in VS Code). Installed `redhat.java` from Open VSX into Kiro. It also needs `pom.xml` **at the root** to resolve dependencies.

### Command cheat sheet

```bash
# database (independent lifecycle from the app — leave it running)
docker compose up -d --wait     # start, block until healthy
docker compose ps               # status
docker compose logs             # postgres logs
docker compose down             # stop, KEEP data
docker compose down -v          # stop and DESTROY data

# the app  (Ctrl+C to stop; holds the terminal, so use a 2nd terminal)
./mvnw spring-boot:run          # compile + run. THIS is how you start/restart.
./mvnw -q compile               # compile only, runs nothing
./mvnw clean spring-boot:run    # wipe target/ first, when Maven seems to run stale code

curl localhost:8080/actuator/health     # {"status":"UP"}

# database access  — NOTE PORT 5433, not 5432
PGPASSWORD=ledger psql -h localhost -p 5433 -U ledger -d ledger
docker exec -it ledger-postgres psql -U ledger -d ledger   # no port/password needed
```

psql meta-commands (no semicolon): `\dt` tables · `\d accounts` describe · `\di` indexes ·
`\x` expanded output · `\timing` · `\q` quit.

GUI options, both already installed: **DBeaver CE** (preferred) and **pgAdmin4 9.17**. Same
credentials; the port is the thing people get wrong.

### Next: Day 2

1. **`V2__add_accounts_owner_index.sql`** — `CREATE INDEX idx_accounts_owner_id ON accounts (owner_id);`
   The primary key indexed `id` automatically; `owner_id` has no index, so "all accounts for this
   user" is a full table scan. **V1 has already run and is immutable** — Flyway stored its checksum,
   so a forgotten index is added in a *new* migration, never by editing V1. That rule is the whole
   point of migrations.
   *(Production would use `CREATE INDEX CONCURRENTLY` to avoid locking writes, but that cannot run
   inside a transaction, which is how Flyway runs migrations. Needs special handling — later.)*

2. **`V3` — the ledger core.** Two tables:
   - **`transactions`**: `id`, `idempotency_key TEXT NOT NULL UNIQUE` (the retry-safety mechanism —
     a `UNIQUE` constraint means a retried request cannot post money twice, enforced by the database
     so it holds even under simultaneous duplicates), `description`, `created_at`.
     **No `status`, no `updated_at`** — the journal is append-only and immutable. Reversals are
     compensating transactions, never `UPDATE` or `DELETE`.
   - **`ledger_entries`**: `id`, `transaction_id REFERENCES transactions(id)`,
     `account_id REFERENCES accounts(id)`, `amount BIGINT NOT NULL` (signed, minor units — 50000 is
     ₹500.00), `currency CHAR(3)`, `created_at`. Plus `CHECK (amount <> 0)` and indexes on
     `account_id` and `transaction_id`.

   **On the money type:** never `FLOAT`/`DOUBLE` — binary floating point cannot represent 0.10
   exactly and errors compound. Signed `BIGINT` minor units (integer arithmetic exact by
   construction, `SUM` cannot drift, sign encodes direction) or `NUMERIC(19,4)` (exact in Postgres,
   more readable). Chose `BIGINT`; the cost is tracking each currency's exponent (INR/USD 2, JPY 0,
   KWD 3).

3. **Then the interesting problem:** the zero-sum invariant — every transaction's entries must sum to
   zero — **cannot be a `CHECK` constraint**, because `CHECK` sees one row and this spans rows.
   Options are application-level enforcement inside a transaction, a deferred constraint trigger, or
   a constrained summary table. This is the heart of the project and the best interview material in it.
